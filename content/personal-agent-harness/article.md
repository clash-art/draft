# personal agent 的 harness 有什么不同

## 01 从对话窗口，到长期助手

办完一件事后，下一件事是另开一次对话，还是继续找同一个助手？

用 personal agent，最吸引我的地方是能把事情交出去。工具还在查资料时，可以继续说新的安排；过几天回来，手里的项目也不用从头讲起。听起来都是很平常的要求。真要让助手做到，光靠每次回答得好，还远远不够。

常见的 thread 界面，很容易让人把一次会话当成一项任务：带着问题来，做完，再开下一段。持续找同一个助手，则会多一层期待：事情可以换，已经交代过的背景和约定还在，没做完的事也有人继续跟进。这说的是产品怎样组织工作，thread 本身同样可以支持记忆、并行和执行中的新要求。

隔几天再聊上周的项目，它还记不记得之前讨论到哪、哪些事情已经定了？这几天有了新进展，也得跟得上。偏好可能几个月都适用，任务状态却可能刚刚更新，光复述旧聊天，往往接不上已经变化的事情。

### 长期助手要满足的四个要求

持续在场：用户关掉窗口，约好的跟进仍要到点触发，长任务继续运行，结果也要回到负责跟进的助手手里。这里至少有三件事：记着何时该开始，能在对话之外执行，完成后有人接住结果。只把“明天下午跟进”存进记忆，还没有把跟进安排好；只让任务跑完、没把结果交回来，也没有完成这次委托。

快速响应：做事途中能收到新要求，还要让它影响接下来的动作。尚未执行的步骤，要重新检查是否继续；已经发出的消息、提交的操作，则不能靠一句“收到”当作没发生。助手需要弄清实际进度，说明哪些已完成、哪些能停、哪些还要用户决定。响应快，不只看回复用了几秒，也看新要求生效之前，是否还在继续做已经不需要的工作。

少让用户操心（hands-off）：事情交出去后，不必盯着每轮推理和工具调用。中断或暂时失败时，应保留原来的目标和已完成进度，能接着做就继续，而不是把同一工作从头再来；结果不确定时先核对，避免重复执行。少操心也不是完全不问：超出授权、目标冲突，或需要用户权衡的重要选择，仍要带着进度和选项回来请用户决定，而不是把权限边界当成一个可以自动跳过的步骤。

主动发现下一步（proactive）：围绕已有目标，从新信息里找到值得继续处理的事。发现线索后，先确认它仍然相关、没有被处理，再判断是否已获准行动。即使能做，也要判断值不值得现在打扰用户：例行进度可以先记下，涉及用户决定或时效的变化，再判断是否需要立刻提醒。“发现了”“可以做”“现在该说”，不是同一个开关。

这些要求也会互相拉扯。先处理新请求，旧工作就可能被打断；让旧工作先跑完，新要求又得多等一会儿。越少让用户盯着，恢复和权限控制就越重要。后台看得越勤，也越要处理误判、重复提醒和运行成本。

所以我看这些助手的公开资料和相关代码时，关心的已经不只是回答得好不好。我想知道，它怎样一边接着和人说话，一边把手里的几件事继续办下去。下面四个案例，刚好能看到这件事的不同部分。

## 02 四个案例，怎样把事情接着做

### Instinct：有用的提醒，要把分散的信息连起来

Kevin Rose 在和 Tim Ferriss 的公开访谈〔1〕里，讲过两次 Instinct 帮上忙的经历。一次是提醒他，有份几天前的 DocuSign 还没签；另一次是把取药通知、当天航班状态和出发时间放在一起，提醒他先去取药，再去机场。

漏签的文件埋在过去的信息里，取药提醒又得结合当天的安排。只把邮件找出来还不够，还要知道哪些事没完成、哪些时间值得一起考虑，才有机会给出这种提醒。Kevin 讲的是使用感受，访谈里没有展开内部实现，不能据此还原 Instinct 的 memory 或调度设计。

不过，这两个例子把长期助手要处理的问题说得很具体：用户没来提问，事情仍在变化；助手需要从已有信息里找出下一步，而不是一直等着新的指令。

找到线索以后，另一个问题马上就来了。用户的新消息、别的 agent 交回的结果、后台发现的事，可能同时到达。先处理谁？

### Grok Bot：用户优先，也有不能随便打断的工作

Grok Bot 的非官方重建代码〔2〕把用户、其他 agent 和后台工作放进不同队列。取下一项工作时，先看用户，再看 agent，最后才是后台。

但排在前面，不代表随时能打断。普通 bot 消息要等当前整轮工作结束；直接发给目标的 priority 消息，可以抢占非用户工作。正在处理的用户任务受保护，群发也拿不到这份优先权。所以，一条消息多久能生效，还得看它有没有抢占权限，以及当前在忙什么。优先级消息可以影响调度，不能替用户批准对外动作。

这个选择也有代价。保护用户任务，可以让正在做的工作少受干扰；普通协作消息却可能等得更久。队列顺序和能否抢占分开，才能同时表达这两种安排。

后台完成工作后，Grok Bot 也不一定马上联系用户。它可以静默运行，真要发消息时，需要明确调用 SendMessage。“事情做完了”和“把这件事告诉用户”，在这里是分开的动作。

这就留下了下一道判断：什么结果值得打扰用户？

### Muse/Hatch：持续发现事情，也得克制地提醒

Muse 的官方设计文〔4〕描述了这样的工作方式：助手按时间和相关事件持续做事，后台结果出来后，再判断要不要提醒。下面提到的具体流程，来自 Muse/Hatch 的非官方二进制归档〔5〕，没有经过线上运行验证。

它会先收集可能值得提醒的事，再判断紧急程度，最后组织消息。每次最多选一项，也可以一项都不选。候选要和最近对话、记忆、历史送达记录对一遍，再决定发出去、缓一缓，还是静默处理。

这一步很有必要。从发现到送达，中间可能已经过了一段时间：用户自己办完了，或者已经收到同一提醒。归档里能看到候选状态、过期时间、按候选键去重和交付账本；还有按未投递积压控制普通与高优先级容量的 SQL，部分时间和积压限制能对上相应代码。

持续发现，也不必每次都启动完整推理。定时任务负责到点触发；monitor 可以先用低成本脚本看看有没有变化，再决定要不要唤醒 agent。

memory 在这里也参与工作。Dreaming 的接口约定，把记忆更新分成先审查、再按确定规则写入的步骤。但记忆里留下了“明天下午跟进”，还不等于明天会执行。把有用的信息留下来，和按时启动任务，仍然需要分别安排。

执行中的新消息，又是另一件事。符合条件时，Muse/Hatch 会把旧请求重新入队，和新输入一起处理。没做完的请求还在，模型却不会从刚才停下的位置接着跑。还有工具没完成、正在前台压缩，或已经开始输出 final，都会挡住这次重启；发过 commentary，则不一定永久失去重启机会。

能不能重新处理请求，要看当时走到了哪一步。工具已经启动后会怎样，还得接着看工具本身。

### dots / Codex：聊天继续了，工具可能还在跑

OpenAI 的 Dominik Kundel 在公开文章〔8〕里提到，dots 基于开源的 Codex harness。下面顺着 Codex 源码看执行中的新消息和工具；这些代码不能直接当成 dots 线上全部实现的说明。

这次查看的 Codex 源码〔6〕把模型推理、工具执行，以及由多次推理和工具调用组成的一轮工作分开处理。启用 InstantInterrupt 的相关路径可以取消当前采样，已经启动的普通工具仍会完成，调用和结果也会保留配对。推理停了，工具造成的外部影响不会自动撤销；普通工具没做完，下一次推理也仍可能要等。

对耗时更长的工作，工具会提供自己的等待方式。exec_command 先等一段可配置的时间：命令结束了，就交回结果；还没结束，就交回进程会话标识，后面继续看同一个进程。等完这一轮，不代表命令结束，更不需要因此重新跑一遍。

codemode 的代码执行单元 cell 也可以独立继续运行。相关路径能提前结束这次等待，交回同一个 cell 标识，cell 本身继续执行。这取决于具体工具和功能路径，并不是所有工具都能随时转入后台。

于是，助手需要同时跟住两边：用户已经聊到了新的事情，原来的进程或 cell 可能还在跑。它得用原标识继续查，等结果回来后，弄清这是哪件事的结果、现在还有没有用，以及是否已经影响了外部系统。

## 03 自己搭 harness 时，我会先想清楚什么

看完这些案例，单独问“能不能记忆”“能不能打断”，还不足以判断一个助手能否长期接住事情。更具体的问题是：用户今天回来，它能找到哪些背景，能核对哪些进度，又能从哪里继续做？

我会先把值得长期留下的信息和正在变化的工作进度分开考虑。用户的背景、沟通偏好、已经确认的重要决定，往后可能反复有用；任务做到哪一步、正在等哪个工具、还有什么需要确认，则会随着执行不断变化。把项目名称和用户偏好记得很牢，却找不到上次工作的进度，用户照样得从头解释。

这里也不能一味追求“记得越多越好”。旧偏好可能变化，已经确认的决定也可能被新的要求取代。要留下什么、何时更新、怎样知道一条信息已经过时，都值得设计。现有材料还不足以还原四家完整的 memory 实现，这部分是搭建长期助手时需要面对的问题，不能假设各家已经用了同一种办法。

这些信息最后还要进入当前上下文，模型才能用它们处理眼前的工作。当前上下文容量有限，不必一直塞着全部历史；需要的时候找回相关背景，再带上最新任务进度，才有机会在隔了一段时间之后继续推进。

摘要和压缩解决的是这部分容量问题。它们可以留下当前对话的重要线索，却不能代替所有长期记忆，也不能成为任务完成与否的唯一凭据。Grok 复用摘要前会核对历史前缀〔3〕，Muse/Hatch 会检查版本、保留快照后的新消息〔5〕，都是因为摘要准备期间，事情还在继续变化。压缩得再及时，漏掉后来发生的变化，接下来的判断也可能建立在旧状态上。

提前做这些准备，会花掉额外预算，也不保证等待完全消失。这里查看的 Codex 当前上下文压缩路径〔7〕仍包含前台等待。背景该保留多少，摘要该多早准备，什么时候必须暂停整理，没有一个适合所有任务的固定答案。

再看新消息到来时的处理。用户希望助手随时能接话，正在做的工作又不能轻易丢下。前面的案例用了队列、受条件限制的重启、推理取消和工具等待等不同办法。它们的取舍也很实际：让新要求更快生效，可能意味着旧工作要重做一部分；保护当前执行，则可能让新消息多等一会儿。自己搭的时候，需要知道哪些工作值得保护，哪些变化值得优先处理，随后怎样接回还没完成的部分。

有了进度记录，恢复也更容易有依据。一次等待结束，进程可能仍在运行；进程真正中断以后，则要先核实哪些步骤已经完成、有没有对外产生影响，再决定怎么继续。尤其是结果不确定的动作，直接重跑可能造成重复。记忆可以帮助理解原来的目标，实际执行到了哪里，还得看相应的任务记录和工具结果。

权限与通知，也要跟着这些变化重新检查。知道用户长期关心某个项目，不等于任何相关动作都已经获准；用户曾经收到过一条提醒，后面也不该因为重新发现同一件事就再发一次。需要用户权衡的时候，带着已有进度回来问；有新结果的时候，结合最新情况判断现在值不值得提醒。后台越积极，这些判断就越影响用户愿不愿意继续把事情交给它。

最后还有调度。把将来的安排写进 memory，仍需要有东西在合适的时间把任务启动起来，再把结果送回负责处理的助手。记住背景、留住进度、按时推进、交回结果，少了任何一环，用户都可能重新变成那个负责追问和收尾的人。

我自己搭 harness 时，会先挑几件真实要交给它的工作，检查哪些信息要长期留下、哪些进度不能丢、哪些选择必须回来问我。再从这些要求出发，决定需要多积极的后台工作、怎样安排打断和恢复，以及愿意为此承担多少等待和运行成本。

# 编辑上下文

## 文章目标与组织

面向小红书读者，分享 personal agent 怎样持续接住被交出去的事情，以及 harness 需要处理的执行问题。以 Instinct、Grok Bot、Muse 和 dots 的公开材料及相关代码为例，语气自然，不写成规格书或研究报告。

保留三个大章节：

1. 从对话窗口，到长期助手。保留与常见 thread 产品心智的对比，以及“长期助手要满足的四个要求”独立小节。
2. 四个案例，怎样把事情接着做。Instinct 放在此章，与 Grok Bot、Muse/Hatch、dots / Codex 并列展开。
3. 自己搭 harness 时，我会先想清楚什么。涵盖背景、进度、memory、上下文压缩、打断与恢复、权限、通知与调度之间的关系。

收尾保留 BoAI 自我介绍、下一篇基于 pi coding agent 从 0 到 1 搭建 personal agent 的预告和自然的关注提示。

## 不要在润色中丢掉的内容

- 四个要求是既定结构，不因追求自然行文而删除或打散：持续在场、快速响应、少让用户操心、主动发现下一步。
- thread 对比说的是默认围绕单项任务的产品心智，不是断言 thread 在技术上不能记忆、并行或 steer。
- 第一章采用“用 personal agent，最吸引我的地方是能把事情交出去。”不要改回“做 personal agent”。
- 第一章用隔几天继续项目、记得已有决定并跟上新进展说明体验；避免把 memory 术语生硬塞进体验描述。这不是全文禁用 memory。
- 实时转向不能只靠一个“先别发”的例子证明与 thread steer 的差异。保留各案例可支持的具体机制及条件，不虚构独有能力。
- 对文章里某句文字的批评只修改该处，不擅自扩大为重构主题或删除整段结构。

## 证据与措辞

- Instinct 访谈是使用经历，不能当作内部 memory 或调度架构的证据。
- Grok Bot 使用非官方重建资料；Muse/Hatch 的具体实现来自非官方二进制归档，不能宣称线上验证。
- 正文介绍 dots，并在正文中说明其基于开源 Codex harness 的公开署名来源。分析 Codex 源码不等于还原 dots 全部线上实现。
- 区分源码可见事实、经验描述和自己的工程判断。没有执行过的测试只能写成测试定义阅读。
- 调度优先级不等于授权；取消推理不等于撤销工具副作用；记下未来安排不等于已经设置调度。
- 不堆一整块泛泛的“资料说明”，把必要的范围限定放到对应案例。出处应能由读者找到，保留标题、作者/仓库、日期、固定版本与路径。

## 文风与排版

- 读起来像在分享自己想明白的事，不机械下定义，不堆术语，也不编造亲身使用经历。
- 改稿后整体通读，检查段落衔接，不只替换局部词语。
- 空白可以用有价值的说明或合适的图补足，但不要为了填满而加废话，也不要把字号放大掩盖内容不足。
- 历史版式正文为 10.5px、行高 1.5；CSS 画布 360 × 600，导出 1440 × 2400。新版本需要重新分页，不应强行锁定历史 11 页。
- 插图使用生图工具，不手搓插画；正文正常排版即可。
- 封面保留“以 Instinct、Grok Bot、Muse 和 dots 为例”的自然简介，不写“4 张图”或阅读时间营销字样。
- 来源索引与 BoAI 介绍、下期提示合并为结尾，避免另外一页只有收尾内容。
- 图片交付时按顺序逐张发送，不报张数、不加逐张编号说明。

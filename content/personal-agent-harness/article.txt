personal agent 的 harness 有什么不同

01 从对话窗口，到长期助手

Kevin Rose 在 Tim Ferriss 的播客〔1〕里讲过两件 Instinct 帮上忙的事。一次是提醒他，几天前有份 DocuSign 还没签。另一次是把取药通知、当天航班状态和出发时间放在一起，提醒他先去取药，再去机场。

这两次他都没有先开口问，提醒还是来了。漏签的文件埋在过去的信息里，取药提醒又得结合当天的安排。只把这几条信息找出来还不够，还要知道哪些事没完成、哪些时间值得一起考虑，才可能给出这样的提醒。

用 personal agent，最吸引我的地方是能把事情交出去。它还在查资料，我可以继续说新的安排。过几天回来，手里的项目也不用从头讲起。这些听起来都很平常，真要做到，光靠每次都答得好还不够。

常见的 thread 界面，很容易让人把一次会话当成一项任务：带着问题来，做完，再开下一段。持续找同一个助手，就会多一层期待：手头的事情可以换，已经交代过的背景和约定还在，没做完的事也有人继续跟进。界面只是其中一层。thread 在技术上一样可以记忆、并行，也能接住执行中的新要求。能不能做到，要看背后的 harness 怎么安排。

隔几天再回来聊上周的项目，它还记不记得之前聊到哪、哪些事已经定了？这几天有了新进展，它也得跟得上。偏好可能几个月都适用，任务状态却可能刚刚变过。只会复述旧聊天，就接不上这些变化。

长期助手要满足的四个要求

持续在场：用户随时找它，它都接得住，关了窗口，交代的事也还在推进。这主要靠两种手段。一是抢占，用户的新消息能先打断手上没那么急的工作。二是把事情交给后台，长命令放进后台进程，成块的工作交给专门的 work agent session，主线腾出来继续跟用户说话。交出去的事，还得记着什么时候该开始，完成后有人接住结果。记忆里写着“明天下午跟进”，到点却没人触发，这次跟进就落空了。任务跑完了，结果却没交回来，这件事也还没办完。

快速响应：事情做到一半，用户提了新要求，助手得接住，还要让它影响接下来的动作。还没做的步骤，得重新看要不要继续。已经发出的消息、提交的操作，不能靠一句“收到”当作没发生，需要改的再补一条更正。助手得弄清实际进度，说明哪些已完成、哪些能停、哪些还要用户决定。所以看响应快不快，要看新要求进来后，它多久停下已经不需要的事。

少让用户操心（hands-off）：事情交出去后，不用盯着每一轮推理和工具调用。中断或暂时失败时，要保留原来的目标和已完成进度，能接着做就接着做，不用把同一件事从头再来一遍。结果不确定时先核对，避免重复执行。该问的时候仍然要问：超出授权、目标对不上，或需要用户拿主意的选择，仍要带着进度和选项回来请用户决定。碰到权限边界，不能自动放行。

主动发现下一步（proactive）：围绕已有目标，从新信息里找出值得接着做的事。发现线索后，先确认它仍然相关、还没有被处理，再判断是否已经获准行动。就算能做，也要判断值不值得现在打扰用户：例行进度可以先记下，涉及用户决定或时间上拖不得的变化，再判断要不要立刻提醒。发现了、可以做、现在该说，是三个不同的判断。

四个要求落到 harness 里，最先碰到的是执行方式。很多 harness 以 session 为中心：同一个 session 里，模型大多沿一条线推理，想一步，发起一个或多个工具调用，拿到结果再想下一步。这期间用户发来新消息，可以排到下一轮，可以在下一个安全点插进当前这一轮（steer），也可以直接打断。steer 一般也要等当前采样或工具调用结束才生效。Codex 和 Claude Code 这三种方式都支持〔9〕〔10〕〔12〕，也能把长命令放到后台进程里跑，把子任务交给专门的 work agent session〔9〕〔10〕〔11〕。

工作分到后台进程或 work agent session 以后，主线就不用一直等着。用户可以接着说话，模型也能先处理别的事，真正用到那个结果时才停下来等。代价是多出一些收尾的活。结果交回来时，得知道它属于哪件事、现在还用不用得上，几份结果要合并去重，它们碰到需要授权的操作，还得把请求送回用户那里。personal agent 的输入来源更多，用户、其他 agent、定时任务、外部事件都可能随时进来，这些活也就更多。下面三个案例，就按这四个要求来看。

Grok Bot：用户优先，也有不能随便抢占的工作

用户发来新消息，别的 agent 交回结果，后台任务又发现了新情况，几件事可能同时到达。先处理谁？

据 Grok Bot 的非官方重建代码〔2〕，用户、其他 agent 和后台任务会进入不同队列，取下一项工作时，先看用户，再看 agent，最后才是后台任务。

但排在前面，不代表随时能抢占。普通 bot 消息要等当前这轮工作结束，直接发给目标的 priority 消息才能抢占非用户工作。正在处理的用户任务受保护，群发也拿不到这份优先权。所以，一条消息多久能生效，还得看它有没有抢占权限，以及当前在忙什么。优先级消息能影响调度，但不能替用户批准对外动作。

后台任务做完后，Grok Bot 也不会自己联系用户。它可以静默运行，要发消息，得明确调用 SendMessage。“事情做完了”和“把这件事告诉用户”，在这份重建代码里是分开的动作。

接下来要判断的是：什么结果值得打扰用户？

Muse/Hatch：持续发现事情，也得克制地提醒

Muse 的官方设计文章〔4〕里说，助手会按时间和相关事件持续做事，这些工作有了结果，再判断要不要提醒。下面的具体流程出自归档〔5〕。

它会先收集可能值得提醒的事，判断紧急程度，最后整理成消息。每次最多选一件，也可以一件都不选。候选要和最近对话、记忆、历史送达记录对一遍，再决定发出去、缓一缓，还是静默处理。

这一步不能省。从发现到送达，中间可能已经过了一段时间：用户自己办完了，或者已经收到同一提醒。归档是一个编译后的二进制文件，候选状态、过期时间、候选键去重、交付账本，以及按未投递积压控制普通和高优先级容量的规则，都能在它内嵌的 SQL 和提示词字符串里看到。

持续发现，也不必每次都启动完整推理。定时任务负责到点触发。要看有没有变化，归档里还有一种叫事件 hook（event hook）的做法：用一个 Bash 轮询脚本检查条件，条件成立时才唤醒负责处理这件事的 agent。归档的文档说，定时检查和事件触发的自动化都是隔一段时间轮询一次〔5〕。

执行中的新消息，又是另一件事。符合条件时，Muse/Hatch 会把旧请求重新入队，和新输入合成一个请求，再处理一遍。重启之后，模型会重新生成回复，但已经跑完的工具结果会不会保留，从归档里确认不了。二进制里还能看到一些和工具阶段、压缩、最终回答之前的门控有关的状态名，看起来重启会在这些阶段受限，但光看字符串说不准。

Codex（dots 的 harness 层）：聊天继续了，工具可能还在跑

OpenAI 的 Dominik Kundel 在公开文章〔8〕里提到，dots 基于开源的 Codex harness。同一篇文章里也说，dots 会主动跟进工作，还能设置按时间或事件触发的自动化。这些是怎么实现的，本文不分析，所以表格里 Codex 这一行的提醒是“—”，持续在场那一格也只写了后台进程。下面从 Codex 的测试定义和相关源码，看执行中的新消息和工具怎么处理。这些材料只能说明 Codex 这一层的情况，不代表 dots 的线上实现全都如此。

Codex 把模型推理、工具执行和整轮 turn 分开管理。任务进行中按 Enter，新指令就会插进当前 turn（steer），按 Tab 则排到下一轮〔9〕。这次看的这个版本里，InstantInterrupt 已经默认开启，但仍标为开发中〔12〕。在这种模式下，新输入可以中止当前采样。已经启动的普通工具还是会跑完，调用和结果也保持配对〔6〕。推理停了，工具造成的外部影响不会自动撤销，得另外处理。普通工具没做完，下一次推理也仍可能要等。

对耗时更长的工作，工具自己也有等待的办法。exec_command 先等一段可配置的时间：命令结束了就交回结果，没结束就交回进程 ID（session_id），之后接着看同一个进程。一次等待结束，不代表命令已经结束，更不用为此重跑一遍。

codemode 的代码执行单元 cell 也能独立继续跑。有些路径能提前结束这次等待，交回同一个 cell 标识，cell 本身继续执行。能不能这样，要看具体工具和功能路径，不是所有工具都能随时转入后台。用户 steer 时，cell 会接着跑。要是直接打断这个 turn，正在跑的 cell 和它嵌套的工具调用会被终止，exec 的后台进程则会留下来〔12〕。

于是，助手得同时跟住两边：用户已经聊到新的事情，原来的进程或 cell 可能还在跑。它要用原来的标识继续查，等结果回来后，弄清这是哪件事的结果、现在还有没有用，以及是否已经对外部系统产生了影响。

03 自己搭 harness 时，我会先想清楚什么

只看“能不能 steer、能不能打断、能不能把工作交出去”，还看不出一个助手能不能长期接住事情。更具体的问题是：用户回来时，它能找到哪些背景，能核对哪些进度，又能从哪里继续做？

记住什么：背景和进度

前面说过，过几天回来，手里的项目不该从头讲起。要做到这一点，助手得留住两类东西。一类是用户的背景、偏好和已经定下的事，往后会反复用到。另一类是任务做到哪一步、在等什么、还有什么要确认，这些随时在变。只记住前者，就找不到上次做到哪，用户还是得再讲一遍。

记住的东西也会过时。上个月的偏好可能早就变了，定好的事也可能被推翻。助手要是照着旧信息办事，用户反而得多操一份心。

放进上下文：摘要和压缩

这些信息还得进入当前上下文，模型才能用它们处理眼前的工作。上下文容量有限，不必一直塞着全部历史。需要时找回相关背景，再带上最新进度，隔一段时间回来也能接着做。

摘要和压缩解决的是这部分容量问题。它们能留下当前对话的重要线索，却不能代替所有长期记忆，也不能成为任务完成与否的唯一凭据。Grok Bot 的重建代码在复用摘要前会核对历史前缀〔3〕，Muse/Hatch 会检查版本、保留快照后的新消息〔5〕，都是因为摘要准备期间，事情还在继续变化。压缩做得再及时，只要漏掉后来发生的变化，接下来的判断就可能建立在旧状态上。

摘要可以趁对话还在进行时提前准备，代价是多花一些模型调用。Codex 默认的上下文压缩〔7〕会让主线停下来，等压缩做完再继续。它最近加了后台压缩〔13〕，目前还在开发中，默认关闭。上下文用到窗口的 65% 时，它先拿一份历史快照，在后台生成摘要，turn 照常往下跑。之后到了检查点再看摘要好了没有，只有这期间历史没变，才把它换进上下文。主线只在换入时停一下。要是后台摘要还没出来，上下文就先满了，主线还是得等它做完。背景留多少、摘要多早开始准备、什么时候必须停下来整理，要看这件任务能接受多少等待和成本。

新消息来了：拆出去的工作怎么收尾

新消息到来时，前面几个案例的处理并不一样。Codex 的进程和 cell 有自己的标识，对话不必为它们停住，但压缩和普通工具仍会让主线等。Muse/Hatch 把新旧输入合成一个请求重跑，能不能重跑，要看已经走到了哪一步。工作拆出去以后，还有些收尾要做。新输入让原来那块不用做了，就停掉它。已经发出去的动作收不回，就再补一步更正。几块并行的结果回来，还得分清哪件是哪件，最后合成一个说法讲给用户。

中断以后：先核实再继续

有了进度记录，恢复也更有依据。一次等待结束，进程可能还在跑。进程真正中断以后，则要先核实哪些步骤已经完成、有没有对外产生影响，再决定怎么继续。尤其是结果不确定的动作，直接重跑可能造成重复。记忆能帮它理解原来的目标，但实际做到哪一步，还得看任务记录和工具结果。

提醒和调度：主动但别打扰

通知也要按最新情况来定。用户曾经收到过一条提醒，后面就不该因为重新发现同一件事再发一次。有新结果的时候，要结合最新情况判断现在值不值得说。需要用户拿主意的时候，带着已有进度回来问。助手越主动，这些判断就越影响用户愿不愿意继续把事情交给它。

最后还有调度。记住了要跟进，还得有东西到点把任务叫起来，再把结果送回负责处理的助手。记住背景、留住进度、按时推进、交回结果，少了哪一环，用户都可能重新变成那个追问和收尾的人。

从哪里开始

我自己搭 harness 时，会先挑几件真要交给它的工作，看哪些能拆出去自己跑，哪些阶段还得留在主线上等。也要看哪些信息得长期留着，哪些进度不能丢，哪些选择必须回来问我。再据此决定助手要多主动、工作拆到多细，以及愿意承担多少等待和运行成本。

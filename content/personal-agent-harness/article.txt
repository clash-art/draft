personal agent 的 harness 有什么不同

01 从对话窗口，到长期助手

Kevin Rose 在 Tim Ferriss 的播客〔1〕里讲过两件 Instinct 帮上忙的事。一次是提醒他，几天前有一份 DocuSign 还没签。另一次是把取药通知、当天的航班状态和出发时间放在一起，提醒他先去取药，再去机场。

这两次他都没有先开口问，提醒是自己来的。漏签的文件埋在过去的信息里，取药提醒又得结合当天的安排才想得到。要给出这样的提醒，得先把这几条信息找出来，还得知道哪些事没完成，哪些时间应该放在一起考虑。

没人问的时候，它也一直跟着这些事。这正是我对 personal agent 最在意的一点。我把事情交给它以后，不用一直盯着。它还在查资料的时候，我可以接着说新的安排。过几天再回来，手里的项目也不用从头讲起。

平时大家用得多的是 thread 驱动的 harness。开一个 thread 往往就为一件事，带着问题来，做完了，再开下一个。如果一直找同一个助手，期待就会多一层。手头的事情可以换，但交代过的背景和约定还在，没做完的事也有人接着跟进。这层期待能不能满足，要看背后的 harness 怎么安排。

比如隔几天回来，接着聊上周的项目，助手得记得之前聊到了哪里，哪些事已经定了。这几天有了新进展，它也得跟得上。偏好可能几个月都适用，任务状态却可能刚刚才变过。只会复述以前的聊天记录，就跟不上这些变化。

长期助手要满足的四个要求

持续在场：用户随时来找，它都能马上回应，关掉窗口以后，交代的事也还在推进。这主要靠三件事。一是抢占，用户的新消息能先打断手上没那么急的工作。二是把耗时的事交出去，长命令放进后台进程，成块的工作交给专门的 work agent session，主线腾出来继续跟用户说话。三是调度和交回，交出去的事要有人按时叫起来，做完以后有人收下结果。记忆里写着“明天下午跟进”，到点却没有东西触发，这次跟进就落空了。任务跑完了，结果却没交回给用户，这件事也还不算办完。

快速响应：事情做到一半，用户提了新要求，助手得马上看到，还要让它影响接下来的动作。还没做的步骤，得重新看要不要继续。已经发出的消息、提交的操作，不能当作没发生过，需要改的就再补一条更正。助手得弄清事情实际进行到哪一步，说明哪些已完成、哪些还能停、哪些要用户决定。所以看响应快不快，要看新要求进来以后，它多久能停下已经不需要的事。

少让用户操心（hands-off）：事情交出去以后，用户不用盯着每一轮推理和工具调用。助手自己往下推进，做完先核对结果，再交回来。该问的时候仍然要问。超出了授权、目标对不上，或者碰到需要用户拿主意的选择，要带着进度和选项回来请用户决定。碰到权限边界，不能自己放行。中途被打断或者暂时失败，也要保留原来的目标和已完成的进度，能接着做就接着做。结果不确定时先核对清楚，避免重复执行。交出去的事得有个地方记着，哪些还没办完、各自在等什么，助手要随时说得清。

主动发现下一步（proactive）：围绕已有的目标，从新信息里找出值得接着做的事。发现线索以后，先确认它仍然相关、还没有被处理过，再判断是不是已经获准行动。就算可以做，也要判断值不值得现在打扰用户。例行进度可以先记下来，涉及用户决定或者时间上拖不得的变化，再判断要不要立刻提醒。发现了、可以做、现在该说，是三个不同的判断。

这四个要求里，有一部分在 thread 驱动的 harness 里已经有现成的做法。Codex 和 Claude Code 都能把用户的新消息排到下一轮，或者插进当前这一轮，能把长命令放进后台进程，也能把子任务交给专门的 work agent session〔6〕〔7〕〔8〕。对 personal agent 来说，在这些做法上需要做的优化有两类。

一类是改这些机制的默认做法。插进当前这一轮的新消息，在 Codex 里叫 steer。它原本要等模型这次输出完，或者等工具调用结束，才交给模型，其他大多数 harness 现在也还是这样〔8〕。personal agent 需要新消息尽快影响正在做的事，效果接近抢占。Codex 最近的改动就接近这种做法。从 10 月发布的 0.163.0 正式版起，它默认打开 instant_interrupt 开关，代码里管这种做法叫 preempt。打开以后，steer 消息一到，harness 就取消正在进行的模型请求，把新消息并进上下文重新请求。已经启动的工具照样跑完，排到下一轮的消息照旧等着〔6〕。

另一类是 thread 驱动的 harness 很少碰到的情况。要少让用户操心，用户多半就不在场，助手得自己把事做完，该问时再把请求送到用户面前。要主动发现下一步，该提醒什么、什么时候说，也都得它自己判断。

02 Grok Bot、Muse、dots 怎么补上这四个要求

三个案例的材料来源各不相同。Grok Bot 的来自非官方重建代码，Muse 的来自非官方二进制归档，dots 的来自它底层的开源 Codex harness 和泄露的 dots 提示词。

Grok Bot

Grok Bot 下功夫最多的是持续在场。用户发来新消息，别的 agent 交回结果，定时任务又到点了，几件事可能同时到达。群聊又多一层。用户在群里说一句，群里几个 bot 轮流发言，轮数有上限，哪一轮没人说话就停。每个 bot 在私聊和各个群里说过的话都记在同一份记录里，群里的发言会标出是哪个群〔4〕。这么多事同时找上来，先处理谁？

根据 Grok Bot 的非官方重建代码〔4〕，用户、其他 agent、定时任务这三种来源的事会进入三个不同的队列。每次做完手上的事、要挑下一件时，Grok Bot 先看用户队列里有没有消息，没有再看其他 agent 发来的。两边都空了，才处理定时任务、交出去的工作跑完后的通知这类事。

排在前面，也还要看能不能抢占。其他 agent 发来的普通消息，要等当前这一轮工作结束。一对一发送时标成 priority 的消息，能打断对方手上不是用户交代的工作，马上把它叫醒〔4〕。正在处理的用户任务受保护。所以，一条消息多久能生效，还得看它有没有抢占权限，以及当前在忙什么。优先级消息能影响调度，但不能替用户批准对外的动作。

工作也可以交出去。Task 工具会把一块工作交给专门的 work agent session，可以让它在后台运行，跑完发一条通知回来〔4〕。它还在跑时，如果用户改了主意，主线可以打断它这一轮，立刻换上新指令。它跑完以后，主线还能接着用同一个 session，让它带着上一次的执行记录继续做。这几项都由开关控制，重建代码里看不出线上默认开了哪些。这个 session 不能直接跟用户说话，碰到需要授权的操作，审批请求还是会送到用户面前〔4〕。

交出去的工作或命令跑完，主线会被叫醒看结果，但不会自动告诉用户。按重建代码里叫醒主线时附带的指令，结果是新的、跟用户有关，或者用户说过要等它，主线才发一条消息告诉用户。过时、重复或者已经处理过的，这次叫醒就静默结束〔4〕。在这份重建代码里，把事做完和告诉用户是两个分开的动作。

Grok Bot 用一份待办清单记着用户交代的事。按重建代码，主线只负责回话和派活，成块的工作交给 work agent session，再用 TodoWrite 工具维护一份待办清单〔4〕。用户提了要求，先记成一条待办，再派出去。每条待办有四种状态：还没开始、进行中、已完成、已取消。几个 session 同时在跑，就有几条待办同时处在进行中。已完成指的是结果已经交到用户手上，session 跑完还不算。主线每次被叫醒，都要先对一遍清单，看哪些在跑、哪些有了结果、下一步派什么。清单存在对话状态里，压缩上下文时，最新的清单会原样带进摘要。服务中途断掉的话，系统会核对没跑完的工作和没回复的消息，再叫醒主线补上〔4〕。

Muse

Muse 下功夫最多的是 proactive。Muse 的官方设计文章〔2〕里说，助手会按时间和相关事件持续做事，这些工作有了结果，再判断要不要提醒用户。下面的材料出自归档。

Muse 主动找用户有三个入口。一是主动推送，每条只带一件值得打扰的事，可能是记忆里值得一提的事、需要关注的目标、一封待读的信，或者最近对话的后续，每条都写明来自哪里。二是 Feed，系统按自己定的时间表生成帖子，每篇都是专门为这个用户写的。三是 Ideas，助手自己想出可以替用户做的事，用户点一下，它就去做〔5〕。

推送会自己控制节奏。普通的事等用户醒着、手头不忙时再送，一天最多一次。时间要紧的放宽一些，真正紧急的马上送。用户想多听什么、不想听什么、什么时段、用什么格式，都记在一个偏好文件里，Muse 每次写推送前都会把它从头读一遍〔5〕。我认为这一层决定的是什么时候说，跟说什么同样要紧。

每次挑选，最多选一件，也可以一件都不选。候选要先和最近的对话、记忆、历史送达记录对一遍，避免推送用户已经办完的事，或者已经收到过的同一条提醒〔5〕。

持续发现，也不必每次都启动完整推理。定时任务负责到点触发。要看有没有变化，归档里还有一种事件 hook（event hook）。它用一个 Bash 轮询脚本检查条件，条件成立时才唤醒负责这件事的 agent〔5〕。Claude Code 的 Monitor 工具思路类似，也是让一个脚本一直盯着，有输出才通知模型。不过 Monitor 的每次监视都有期限，默认 5 分钟，最长 30 分钟，到期就结束，会话结束也会停〔8〕。Muse 的事件 hook 跟定时任务一样属于自动化，按固定间隔轮询，没有这个期限。我认为这让 Muse 的 proactive 粒度更细。它可以盯住一个具体条件，条件一变就叫醒负责的 agent，用不着等下一次定时任务，用户不在场时也能一直挂着。

Muse 把答应过的事建成跟踪项。拿机票来说，邮箱里来了一封航班确认，助手不用问用户，先查有没有同一趟行程的跟踪项。没有就建一个，再把比价和航班动态两个定时任务挂上去。跟踪项结束，这两个任务一起删掉〔5〕。预订、快递、提醒、出行这类超出当前对话的事，用户没说要跟，助手也要建一个跟踪项。订好了、付完款，只要后续的事还没完，跟踪项就一直开着。跟踪项和用户自己设的目标分开存。

每个跟踪项有一行当前状态，写最新的结果、在等什么，或者卡在哪里。助手每记一条进展，系统都会看这一行要不要跟着更新。用户说过某天前没回音就提醒我，这个条件可以记成一条升级规则，到期时告诉用户，或者请用户决定。每个跟踪项还配一个笔记文件，记助手自己的工作笔记，接着做之前要先读它。跟踪项只分进行中和已完成两种状态。工具说明要求，有证据表明事情已经结束，比如快递签收、活动结束、用户取消，就主动关掉。光是一直没动静，或者只做完其中一步，都不算结束。

对外发送、付款这类操作，每次都要用户批准，审批会推送到手机上〔5〕。归档里也有对不上的地方。文档说，定时任务这类没人在旁边的任务，可以停在审批卡片上等用户。二进制里给脱离对话运行的 worker 的提示词却说，审批可能永远等不来，要当作失败，换别的办法。实际运行时按哪一种来，光看归档判断不了。

执行中来了新消息，只要模型还没调用工具、没开始输出最终回复，Muse 会把旧请求和新消息合成一个请求重跑。如果工具已经发出去、正在压缩上下文，或者新消息来源不同，新消息就排到这一轮之后〔5〕。

dots

dots 这一节主要看两件事。一是 Codex 这一层的快速响应。二是 dots 怎么做主动发现：Dreamer 负责找新情况，要不要告诉用户由主助手决定。

OpenAI 的 Dominik Kundel 在公开文章〔3〕里提到，dots 基于开源的 Codex harness。同一篇文章里也说，dots 会主动跟进工作，还能设置按时间或事件触发的自动化。主动跟进靠的是 dots 自己加的一层。按泄露的 dots 提示词〔9〕，主助手会派出一个叫 Dreamer 的调研 agent，按心跳定时运行。它先读最近的对话、用户笔记和待办，再去已连接的应用里找新情况。Dreamer 不能联系用户，也不能替用户做事。只有发现有用的新东西，或者碰到要主助手处理的阻碍时，它才通知主助手一次，告不告诉用户由主助手决定。每天凌晨还有一次复盘，回顾当天的对话，更新用户的偏好和优先级。Muse 让一个 agent 自己挑一件事提醒，dots 则让一个 agent 负责发现，另一个决定说不说。开源 Codex 里找不到 Dreamer，只能看到它把定时心跳触发的消息和用户亲自发的消息分开记录〔6〕。

Dreamer 读的待办，是共享记忆里的一个文件。按泄露的 dots 技能说明，主助手把用户重要的待办、承诺和截止日期都记在这里〔9〕。用户没提、还没开始做的事，只要对用户重要，也要记上。每条待办有四种状态：待办、进行中、已完成、已取消。卡点另外记三栏：是不是卡住了，被清单里哪几条卡住，现在在等谁。在等谁分成等用户、等助手自己、等别人或外部服务，以及什么都不等。确认结果已经达成，才能标成已完成。截止日期过了，也要先查清发生了什么。关掉的事留七天，再挪进归档。这份文件由主助手或负责记忆的 work agent session 来改。Dreamer 只读不改，调研完告诉主助手哪些该加、该改、该关〔9〕。

执行中来的新消息和正在跑的工具怎么处理，要看底层的 Codex。下面几段来自 Codex 的测试定义和源码，只能说明 Codex 这一层的情况，dots 的线上实现可能另有做法。

Codex 把模型推理、工具执行和整轮 turn 分开管理。任务进行中，用户的新指令有两种发法，steer 插进当前 turn，queue 排到下一轮〔7〕。插进当前 turn 的新指令，现在默认会直接中止当前推理，已经启动的工具还是会跑完〔6〕。推理停了，工具造成的外部影响不会自动撤销，得另外处理。工具没做完，下一次推理也可能要等。

耗时长的命令，Codex 会先等一会儿。跑完了就交回结果，没跑完就交回一个进程 ID，之后接着查同一个进程，不用重跑一遍。

打开还在开发中的 Code Mode 后，模型写的代码片段也能这样转到后台继续跑。用户 steer 时，它会接着跑。直接打断这个 turn，它就会被终止，长命令的后台进程则会留下来〔6〕。

于是，助手得同时顾着两边。用户已经聊到新的事情，原来的命令或代码可能还在跑。它要用原来的标识继续查，等结果回来后，弄清这是哪件事的结果、现在还有没有用，以及是否已经对外部系统产生了影响。

03 自己搭 harness，哪些做法值得借鉴

三家各有所长。如果我们要自己实现一个 harness for personal agent，还得往下想几个技术问题：几件事同时来了谁先处理，用户改主意时正在做的事怎么停，用户不在时事情怎么记、怎么等，什么时候该开口，记住的东西怎么保持新鲜。下面一个个看，各家有哪些做法值得借鉴。

几件事同时找上门，谁先说话

用户的消息排第一，这一点没什么争议。难的是别的事什么时候能插队。这里 Grok Bot 的做法值得借鉴。用户、其他 agent、定时任务各排一队，标成 priority 的消息能打断不是用户交代的工作，正在处理的用户任务受保护〔4〕。主线只负责回话和派活，成块的工作交给 work agent session，所以用户找它时总能回话〔4〕。

用户改主意时，正在做的事怎么停

用户让助手比较三家酒店，比到一半说只看第二家。还在查另外两家的 session 该停掉，已经发出的询价邮件收不回，就补一封说明。这里 Codex 的 preempt 值得借鉴，新消息一到就中止推理，已经启动的工具照样跑完〔6〕。工具还没发出去时，Muse 把新旧消息合成一个请求重跑〔5〕。对派出去的 session，Grok Bot 和 Codex 都能发新指令，必要时打断它这一轮〔4〕〔6〕。

压缩上下文时，Grok Bot 和 Muse 还接着处理新消息，主线不用停下来等〔4〕〔5〕。我认为 personal agent 值得多花这些 token，因为用户只想把事交出去，马上听到一句记下了。

用户不在时，事情怎么记、怎么等

答应过的事要有地方记。Muse 的跟踪项值得借鉴，用户没说要跟也建，每项一行当前状态，拿到证据才关掉〔5〕。再加上 dots 待办文件里那一栏，写清每件事在等谁〔9〕。审批送到用户手机上〔5〕，等审批的那几个小时里，别的事照常往下做。

等外部变化，我认为 Muse 的事件 hook 最值得借鉴。常见做法是靠定时任务到点叫醒 agent 看一眼，没变化也要跑一次推理，间隔设长了又会错过。Muse 用一个轮询脚本检查条件，条件成立才叫醒负责的 agent，没有期限，用户不在时也一直挂着〔5〕。盯票价、等快递、等对方回邮件都适合这样做。平时不用跑推理，条件一变马上就能开口。

什么时候该开口

发现了、可以做、现在该说，是三个不同的判断。dots 把发现交给 Dreamer，它不能联系用户，说不说由主助手决定〔9〕。我认为 Muse 把现在该说这一步做得最细。每条推送只带一件事，普通的事等用户醒着、不忙时再送，一天最多一次。用户的偏好写进文件，写推送前先读〔5〕。

记住的东西怎么保持新鲜

Grok Bot 每轮对话结束都提取该记的事〔4〕。Muse 每小时把新对话并进记忆一次，每晚再回看一遍〔5〕。两家都比 Claude Code 由模型自己判断要不要记更勤〔8〕。记得多，过时的也多。两家都用新的说法覆盖旧的，Grok Bot 还让旧记忆慢慢淡出〔4〕〔5〕。压缩时再顺带换上最新的记忆，助手就不会照着上个月的偏好办事。

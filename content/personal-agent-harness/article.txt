personal agent 的 harness 有什么不同

这篇想聊的是：personal agent 要长期接住交出去的事情，harness 得处理哪些执行问题。我会先讲长期助手要满足的四个要求，再拆 Grok Bot、Muse/Hatch 和 dots / Codex 三个实现，看它们各自从哪一层把串行的执行线拆开，最后说说自己搭 harness 时会先想清楚什么。文中的代码出处都标了固定版本。

这四个要求要同时成立，难点通常在执行方式，而不在要求本身。旧的会话只有一条串行的线，模型说一轮、调一次工具、再等下一轮；新消息进来，不是等着，就是打断。把线拆开之后，后台要多主动、成本要花到什么程度、权限检查要放在哪一步，都可以按需要调。

01 从对话窗口，到长期助手

Kevin Rose 在 Tim Ferriss 的公开访谈〔1〕里，讲过两件 Instinct 帮上忙的事（他讲的是使用感受，没有展开内部实现）。一次是提醒他，几天前有份 DocuSign 还没签；另一次是把取药通知、当天航班状态和出发时间放在一起，提醒他先去取药，再去机场。

这两次他都没有先开口问，提醒还是来了。漏签的文件埋在过去的信息里，取药提醒又得结合当天的安排。只把这几条信息找出来还不够，还要知道哪些事没完成、哪些时间值得一起考虑，才可能给出这样的提醒。

一件事办完，下一件事是另开一次对话，还是继续找同一个助手？

用 personal agent，最吸引我的地方是能把事情交出去。它还在查资料，我可以继续说新的安排；过几天回来，手里的项目也不用从头讲起。这些听起来都很平常，真要做到，光靠每次都答得好还不够。

常见的 thread 界面，很容易让人把一次会话当成一项任务：带着问题来，做完，再开下一段。持续找同一个助手，就会多一层期待：手头的事情可以换，已经交代过的背景和约定还在，没做完的事也有人继续跟进。这更多是产品组织工作的方式不同。thread 在技术上一样可以记忆、并行，也能接住执行中的新要求。

隔几天再回来聊上周的项目，它还记不记得之前聊到哪、哪些事已经定了？这几天有了新进展，它也得跟得上。偏好可能几个月都适用，任务状态却可能刚刚变过；只复述旧聊天，往往接不上已经变化的事情。

长期助手要满足的四个要求

持续在场：用户关了窗口，约好的跟进仍要到点触发，长任务还能继续跑，结果也要回到负责跟进的助手手里。至少得做到三件事：记着什么时候该开始，能在对话之外执行，完成后有人接住结果。只把“明天下午跟进”存进记忆，不等于已经把跟进安排好；只让任务跑完、没把结果交回来，也不算完成了这次委托。

快速响应：事情做到一半，用户提了新要求，助手得接住，还要让它影响接下来的动作。还没做的步骤，得重新看要不要继续；已经发出的消息、提交的操作，不能靠一句“收到”当作没发生，需要改的再补一条更正。助手得弄清实际进度，说明哪些已完成、哪些能停、哪些还要用户决定。响应快不快，不只看回复用了几秒，也看新要求进来后，它是不是还在做已经不需要的事。

少让用户操心（hands-off）：事情交出去后，不用盯着每一轮推理和工具调用。中断或暂时失败时，要保留原来的目标和已完成进度，能继续就继续，而不是把同一件事从头再来一遍；结果不确定时先核对，避免重复执行。少操心也不是完全不问：超出授权、目标对不上，或需要用户拿主意的选择，仍要带着进度和选项回来请用户决定。碰到权限边界，不能自动放行。

主动发现下一步（proactive）：围绕已有目标，从新信息里找出值得接着做的事。发现线索后，先确认它仍然相关、还没有被处理，再判断是否已经获准行动。就算能做，也要判断值不值得现在打扰用户：例行进度可以先记下，涉及用户决定或时间上拖不得的变化，再判断要不要立刻提醒。“发现了”“可以做”“现在该说”，不是同一个开关。

这些要求落到同一条执行线上，问题就变成了：谁先跑，谁等着，哪里可以拆开。所以我看这些助手的公开资料和代码时，不只看它们回答得好不好，更想知道它们各自从哪里把线拆开：有的让输入先排队，有的让旧请求重新入队，还有的让工具和推理各自跑。分开之后，哪些事能并行，哪里还得等，等待最后留在了哪个环节，才是各家真正的差别。下面三个案例，正好各展示了其中一部分。

02 三个案例，怎样把事情接着做

先把三个案例放在一起看（“—”表示文中没有涉及）：

| | 打断 | 提醒 | 恢复 | 调度 |
|---|---|---|---|---|
| Grok Bot | priority 消息可抢占非用户工作；正在处理的用户任务受保护 | 后台可静默运行，要发消息得明确调用 SendMessage | — | 三类队列：先用户，再 agent，最后后台 |
| Muse/Hatch | 符合条件时，旧请求重新入队，和新输入一起处理 | 每次最多选一项，也可不选；对照最近对话、记忆和送达记录 | 旧请求还在，但不从停下的位置接着跑 | 定时任务到点触发；monitor 先用低成本脚本看变化 |
| dots / Codex | InstantInterrupt 相关路径可取消当前采样，已启动的普通工具仍会完成 | — | 用原来的进程会话或 cell 标识继续查 | — |

Grok Bot：用户优先，也有不能随便打断的工作

用户发来新消息，别的 agent 交回结果，后台又发现了新情况，几件事可能同时到达。先处理谁？

Grok Bot 的非官方重建代码〔2〕把用户、其他 agent 和后台工作放进不同队列。取下一项工作时，先看用户，再看 agent，最后才是后台。

但排在前面，不代表随时能打断。普通 bot 消息要等当前这轮工作结束；直接发给目标的 priority 消息，可以抢占非用户工作。正在处理的用户任务受保护，群发也拿不到这份优先权。所以，一条消息多久能生效，还得看它有没有抢占权限，以及当前在忙什么。优先级消息能影响调度，但不能替用户批准对外动作。

把工作分进不同队列，也不代表不用等。保护用户任务时，普通协作消息可能要等在后面，直到当前这轮工作结束。等待只是被挪到了队列里的不同位置。先做谁、能不能抢占，仍是两件要分开定的事。

后台完成工作后，Grok Bot 也不会自己联系用户。它可以静默运行，要发消息，得明确调用 SendMessage。“事情做完了”和“把这件事告诉用户”，在这里是分开的动作。

接下来要判断的是：什么结果值得打扰用户？

Muse/Hatch：持续发现事情，也得克制地提醒

Muse 的官方设计文章〔4〕里说，助手会按时间和相关事件持续做事，后台有结果后，再判断要不要提醒。下面的具体流程出自归档〔5〕。

它会先收集可能值得提醒的事，判断紧急程度，最后整理成消息。每次最多选一件，也可以一件都不选。候选要和最近对话、记忆、历史送达记录对一遍，再决定发出去、缓一缓，还是静默处理。

这一步不能省。从发现到送达，中间可能已经过了一段时间：用户自己办完了，或者已经收到同一提醒。归档里有候选状态、过期时间、候选键去重和交付账本；还有一段 SQL，按未投递积压控制普通和高优先级容量。其中一些时间限制和积压上限，能在代码里找到对应。

持续发现，也不必每次都启动完整推理。定时任务负责到点触发；monitor 可以先用低成本脚本看看有没有变化，再决定要不要唤醒 agent。

执行中的新消息，又是另一件事。符合条件时，Muse/Hatch 会把旧请求重新入队，和新输入一起处理。没做完的请求还在，模型却不会从刚才停下的位置接着跑。如果工具还没跑完、正在前台压缩，或者已经开始输出 final，这次重启就会被挡住；发过 commentary，不一定永久失去重启机会。

能不能重新处理请求，要看当时走到了哪一步。工具启动之后会怎样，还得看具体是哪种工具。

dots / Codex：聊天继续了，工具可能还在跑

OpenAI 的 Dominik Kundel 在公开文章〔8〕里提到，dots 基于开源的 Codex harness。下面从 Codex 的测试定义和相关源码，看执行中的新消息和工具怎么处理。这些材料只能说明 Codex 这一层的情况，不代表 dots 的线上实现全都如此。

Codex 这套实现把模型推理、工具执行，以及由多次推理和工具调用组成的一轮工作，分开处理。测试定义〔6〕里还能看到：启用 InstantInterrupt 的相关路径可以取消当前采样，已经启动的普通工具仍会完成，调用和结果也会保留配对。推理停了，工具造成的外部影响不会自动撤销，得另外处理；普通工具没做完，下一次推理也仍可能要等。

对耗时更长的工作，工具自己也有等待的办法。exec_command 先等一段可配置的时间：命令结束了，就交回结果；还没结束，就交回进程会话标识，后面继续看同一个进程。一次等待结束，不代表命令已经结束，更不用为此重跑一遍。

codemode 的代码执行单元 cell 也能独立继续跑。有些路径能提前结束这次等待，交回同一个 cell 标识，cell 本身继续执行。能不能这样，要看具体工具和功能路径，不是所有工具都能随时转入后台。

于是，助手得同时跟住两边：用户已经聊到新的事情，原来的进程或 cell 可能还在跑。它要用原标识继续查，等结果回来后，弄清这是哪件事的结果、现在还有没有用，以及是否已经对外部系统产生了影响。

03 自己搭 harness 时，我会先想清楚什么

只看“能不能打断”“有没有后台”，还看不出一个助手能不能长期接住事情。更具体的问题是：用户回来时，它能找到哪些背景，能核对哪些进度，又能从哪里继续做？

前面说过，过几天回来，手里的项目不该从头讲起。要做到这一点，助手得留住两类东西：一类是用户的背景、偏好和已经定下的事，往后会反复用到；另一类是任务做到哪一步、在等什么、还有什么要确认，随时在变。只记住前者，就找不到上次做到哪，用户还是得再讲一遍。

记住的东西也会过时。上个月的偏好可能早就变了，定好的事也可能被推翻；助手要是照着旧信息办事，用户反而得多操一份心。

这些信息还得进入当前上下文，模型才能用它们处理眼前的工作。上下文容量有限，不必一直塞着全部历史；需要时找回相关背景，再带上最新进度，隔一段时间再回来，也能接着做。

摘要和压缩解决的是这部分容量问题。它们能留下当前对话的重要线索，却不能代替所有长期记忆，也不能成为任务完成与否的唯一凭据。Grok 在复用摘要前会核对历史前缀〔3〕，Muse/Hatch 会检查版本、保留快照后的新消息〔5〕，都是因为摘要准备期间，事情还在继续变化。压缩做得再及时，只要漏掉后来发生的变化，接下来的判断就可能建立在旧状态上。

提前做这些准备，会多花一些成本，也不保证不用等。这次看的 Codex 当前上下文压缩路径〔7〕仍包含前台等待。背景该留多少，摘要该多早准备，什么时候必须停下来整理，没有一个适合所有任务的固定答案。

新消息到来时怎么处理，问题就变成了：哪些工作能拆成独立的一块继续跑，哪里还得串行地等。进程和 cell 可以有自己的标识，对话不必为它们停住；但压缩、普通工具的完成，以及 Muse/Hatch 那种有条件的重启，仍会把等待留在具体环节上。拆开之后，还有些收尾要做：新输入让原来那块不用做了，就停掉它；已经发出去的动作收不回，就再做一步更正。几块并行的结果回来，还得说清哪件是哪件，最后合成一个说法讲给用户。

有了进度记录，恢复也更有依据。一次等待结束，进程可能还在跑；进程真正中断以后，则要先核实哪些步骤已经完成、有没有对外产生影响，再决定怎么继续。尤其是结果不确定的动作，直接重跑可能造成重复。记忆能帮它理解原来的目标，但实际做到哪一步，还得看任务记录和工具结果。

权限和通知，也不能只按老印象来。知道用户长期关心某个项目，不等于任何相关动作都已经获准；用户曾经收到过一条提醒，后面也不该因为重新发现同一件事就再发一次。需要用户拿主意的时候，带着已有进度回来问；有新结果的时候，结合最新情况判断现在值不值得提醒。后台越积极，这些判断就越影响用户愿不愿意继续把事情交给它。

最后还有调度。记住了要跟进，还得有东西到点把任务叫起来，再把结果送回负责处理的助手。记住背景、留住进度、按时推进、交回结果，少了哪一环，用户都可能重新变成那个追问和收尾的人。

我自己搭 harness 时，会先挑几件真要交给它的工作，看这条线从哪里拆开：哪些能独立跑，哪些阶段还得等。也要看哪些信息得长期留着，哪些进度不能丢，哪些选择必须回来问我。再据此决定后台要多积极、拆到多细，以及愿意承担多少等待和运行成本。

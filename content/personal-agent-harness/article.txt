personal agent 的 harness 有什么不同

01 从对话窗口，到长期助手

Kevin Rose 在 Tim Ferriss 的播客〔1〕里讲过两件 Instinct 帮上忙的事。一次是提醒他，几天前有份 DocuSign 还没签。另一次是把取药通知、当天航班状态和出发时间放在一起，提醒他先去取药，再去机场。

这两次他都没有先开口问，提醒还是来了。漏签的文件埋在过去的信息里，取药提醒又得结合当天的安排。要给出这样的提醒，得先把这几条信息找出来，还要知道哪些事没完成、哪些时间值得一起考虑。

这种提醒背后，是我对 personal agent 最在意的一点：事情交出去以后，不用一直盯着。它还在查资料，我可以继续说新的安排。过几天回来，手里的项目也不用从头讲起。这些听起来都很平常，真要做到，每次答得好只是起点。

这和平时用 thread 的感觉不太一样。常见的 thread 界面，很容易让人把一次会话当成一项任务：带着问题来，做完，再开下一段。持续找同一个助手，就会多一层期待：手头的事情可以换，已经交代过的背景和约定还在，没做完的事也有人继续跟进。界面只是其中一层。thread 在技术上一样可以记忆、并行，也能接住执行中的新要求。能不能做到，要看背后的 harness 怎么安排。

隔几天再回来聊上周的项目，它还记不记得之前聊到哪、哪些事已经定了？这几天有了新进展，它也得跟得上。偏好可能几个月都适用，任务状态却可能刚刚变过。只会复述旧聊天，就接不上这些变化。

长期助手要满足的四个要求

持续在场：用户随时找它，它都接得住，关了窗口，交代的事也还在推进。这主要靠三件事。一是抢占，用户的新消息能先打断手上没那么急的工作。二是把事情交给后台，长命令放进后台进程，成块的工作交给专门的 work agent session，主线腾出来继续跟用户说话。三是调度和交回，交出去的事要有人按时叫起来，完成后有人接住结果。记忆里写着“明天下午跟进”，到点却没人触发，这次跟进就落空了。任务跑完了，结果却没交回来，这件事也还没办完。

快速响应：事情做到一半，用户提了新要求，助手得接住，还要让它影响接下来的动作。还没做的步骤，得重新看要不要继续。已经发出的消息、提交的操作，不能靠一句“收到”当作没发生，需要改的再补一条更正。助手得弄清实际进度，说明哪些已完成、哪些能停、哪些还要用户决定。所以看响应快不快，要看新要求进来后，它多久停下已经不需要的事。

少让用户操心（hands-off）：事情交出去以后，用户不用盯着每一轮推理和工具调用。助手自己往下推进，做完先核对结果，再交回来。该问的时候仍然要问：超出授权、目标对不上，或需要用户拿主意的选择，要带着进度和选项回来请用户决定。碰到权限边界，不能自动放行。中途中断或暂时失败，也要保留原来的目标和已完成进度，能接着做就接着做，结果不确定时先核对，避免重复执行。

主动发现下一步（proactive）：围绕已有目标，从新信息里找出值得接着做的事。发现线索后，先确认它仍然相关、还没有被处理，再判断是否已经获准行动。就算能做，也要判断值不值得现在打扰用户：例行进度可以先记下，涉及用户决定或时间上拖不得的变化，再判断要不要立刻提醒。发现了、可以做、现在该说，是三个不同的判断。

这四个要求里，快速响应和交出去工作，编程 agent 已经有现成做法。Codex 和 Claude Code 都能把用户的新消息排到下一轮、插进当前这一轮，或者直接打断，也能把长命令放进后台进程，把子任务交给专门的 work agent session〔9〕〔10〕〔11〕〔12〕〔16〕。personal agent 难在其他几处：用户多半不在场，叫醒它的可能是定时任务或外部事件，交出去的结果要有人接住，该提醒什么也得它自己判断。下面看三个案例各自怎么补。

Grok Bot：用户优先，也有不能随便抢占的工作

用户发来新消息，别的 agent 交回结果，后台任务又发现了新情况，几件事可能同时到达。先处理谁？

据 Grok Bot 的非官方重建代码〔2〕，用户、其他 agent 和后台任务会进入不同队列，取下一项工作时，先看用户，再看 agent，最后才是后台任务。

排在前面，也还要看能不能抢占。普通 bot 消息要等当前这轮工作结束，直接发给目标的 priority 消息才能抢占非用户工作。正在处理的用户任务受保护。所以，一条消息多久能生效，还得看它有没有抢占权限，以及当前在忙什么。优先级消息能影响调度，但不能替用户批准对外动作。

工作也可以交出去。Task 工具会把一块工作交给专门的 work agent session，可以让它在后台运行，跑完发一条通知回来〔15〕。它还在跑时，用户改了主意，主线可以打断它这一轮，立刻换上新指令。它跑完以后，主线还能接着用同一个 session，让它带着上一次的执行记录继续做。这几项都由开关控制，重建代码里看不出线上默认开了哪些。这个 session 不能直接跟用户说话，碰到需要授权的操作，审批请求还是会送到用户面前〔17〕。

后台任务做完后，Grok Bot 也不会自己联系用户。它可以静默运行，要告诉用户，得专门发一条消息。“事情做完了”和“把这件事告诉用户”，在这份重建代码里是分开的动作。

接下来要判断的是：什么结果值得打扰用户？

Muse/Hatch：持续发现事情，也得克制地提醒

Muse 的官方设计文章〔4〕里说，助手会按时间和相关事件持续做事，这些工作有了结果，再判断要不要提醒。下面的具体流程出自归档〔5〕。

它会先收集可能值得提醒的事，判断紧急程度，最后整理成消息。每次最多选一件，也可以一件都不选。候选要和最近对话、记忆、历史送达记录对一遍，再决定发出去、缓一缓，还是静默处理。

这一步不能省。从发现到送达，中间可能已经过了一段时间：用户自己办完了，或者已经收到同一提醒。归档是一个编译后的二进制文件，去重、过期和送达记录这些规则，都能在里面看到。

持续发现，也不必每次都启动完整推理。定时任务负责到点触发。要看有没有变化，归档里还有一种叫事件 hook（event hook）的做法：用一个 Bash 轮询脚本检查条件，条件成立时才唤醒负责处理这件事的 agent。归档的文档说，定时检查和事件触发的自动化都是隔一段时间轮询一次〔5〕。

执行中的新消息，又是另一件事。符合条件时，Muse/Hatch 会把旧请求重新入队，和新输入合成一个请求，再处理一遍。重新处理时，模型会重新生成回复。这一轮之前已经调用过的工具，是沿用原来的结果，还是再调用一遍，归档资料里看不出来。

交出去的事，Muse/Hatch 也尽量让它自己做完。按归档里的文档，定时任务在用户关掉 app 时照常运行，结果作为消息发到对话里。对外发送、付款这类操作，每次都要用户批准，审批会推送到手机上〔19〕。有些 worker 在报告完成前，要先验证做出来的东西确实能用。归档里也有对不上的地方。文档说后台任务可以停在审批卡片上等用户，二进制里给脱离对话运行的 worker 的提示词却说，审批可能永远等不来，要当作失败换别的办法。实际运行时按哪一种来，光看归档判断不了。

dots 底层的 Codex harness：聊天继续了，工具可能还在跑

OpenAI 的 Dominik Kundel 在公开文章〔8〕里提到，dots 基于开源的 Codex harness。同一篇文章里也说，dots 会主动跟进工作，还能设置按时间或事件触发的自动化。这些是怎么实现的，本文不分析，所以表格里 dots 这一行只写 Codex harness 能看到的部分，提醒一格是“—”。下面从 Codex 的测试定义和相关源码，看执行中的新消息和工具怎么处理。这些材料只能说明 Codex 这一层的情况，dots 的线上实现可能另有做法。

Codex 把模型推理、工具执行和整轮 turn 分开管理。任务进行中按 Enter，新指令就会插进当前 turn（steer），按 Tab 则排到下一轮〔9〕。新输入还可以直接中止当前推理，已经启动的工具还是会跑完〔6〕〔12〕。推理停了，工具造成的外部影响不会自动撤销，得另外处理。工具没做完，下一次推理也可能要等。

耗时长的命令，会先等一会儿。跑完了就交回结果，没跑完就交回一个进程 ID，之后接着查同一个进程，不用重跑一遍。

代码执行有些情况下也能这样转到后台继续跑。用户 steer 时，它会接着跑。直接打断这个 turn，它就会被终止，长命令的后台进程则会留下来〔12〕。

Codex 也能把子任务交给专门的 work agent session。这项功能是稳定版，默认开启〔16〕。主线可以开一个 session 让它自己跑，跑完会收到通知。它还在跑时，主线能给它发新指令，必要时立刻打断，让它改方向。关掉的 session 之后还能恢复，接着收指令。子任务碰到需要授权的操作，审批会出现在它自己的线程里，终端界面会提示用户切过去处理。主线 agent 这边看到的状态仍是“在运行”，不知道它在等审批〔18〕。

于是，助手得同时跟住两边：用户已经聊到新的事情，原来的命令、代码执行或 work agent session 可能还在跑。它要用原来的标识继续查，等结果回来后，弄清这是哪件事的结果、现在还有没有用，以及是否已经对外部系统产生了影响。

03 自己搭 harness 时，我会先想清楚什么

前两节讲了长期助手要满足的四个要求，也看了三个案例各自怎么做。轮到自己搭，先要看清它和常见的 coding agent harness 差在哪。常见的 harness 以 thread 为单位。用户开一个 thread，交代一件事，在旁边看着它做，做完这个 thread 就告一段落。Codex 就是这样，恢复一个 thread 时，读回的是这个 thread 自己的历史，跨 thread 的记忆功能默认关闭〔22〕。personal agent 要连续在线好几天，手上同时挂着几件事。叫醒它的可能是用户，也可能是定时任务，或者交出去的工作跑完了，这时用户多半不在场。下面几件事，thread 里都有对应的做法，放到这种场景下，要求就变了。

记住什么：更勤、更宽，也看得更多

编程 agent 也有记忆，personal agent 在这件事上更激进。

先是记得更勤。Grok Bot 的重建代码里，每轮对话结束都会再跑一遍模型，从这一轮里提取该记的事，隔几轮还会写一条经过记录〔23〕。Muse/Hatch 有定时整理记忆的任务，每小时把新对话并进记忆文件，每晚再回看一遍最近的对话〔24〕。Claude Code 的自动记忆由模型自己判断要不要写，官方文档也说它不会每次都记〔25〕。Codex 的记忆功能默认关闭，打开后也只在新会话开始时，回头整理以前的会话〔26〕。

记的范围也更宽。Grok Bot 除了用户档案，还记经过日志，以及同一用户所有助手共享的用户事实。Muse/Hatch 给每个人、每个群单独建档。编程 agent 记的主要是项目相关的东西。

记忆也跟着压缩更新。Grok Bot 每轮都把记忆放进系统提示，压缩时顺带换上最新的记忆。Muse/Hatch 的二进制里有压缩前先写一次记忆的字样，文档里没有对应说明。Claude Code 压缩以后，会重新读一遍用户写的记忆文件〔25〕。

最明显的差别，是 personal agent 会主动去看自己派出去的 session 做了什么。Grok Bot 能看到每个还在跑的 work agent session 最近调用了哪些工具，也能读它的实时运行记录。系统提示要求它主动去查，告诉用户「还在跑」之前尤其要查一遍〔27〕。Muse/Hatch 的回看主要交给定时任务，每晚回看最近的对话。编程 agent 默认只拿结果。Codex 的主线等子任务结束，拿到的是它最后一条消息。Claude Code 的子任务只交回一份总结，运行记录虽然存在磁盘上，却没有工具或提示让它去读。Codex 要打开记忆功能，才会回头整理以前的会话。

记得多，代价是记住的东西也会过时。上个月的偏好可能早就变了，定好的事也可能被推翻。Grok Bot 和 Muse/Hatch 都会用新的说法覆盖旧的，Grok Bot 还会让旧记忆慢慢淡出〔23〕〔24〕。助手要是照着旧信息办事，用户反而得多操一份心。

放进上下文：一条不结束的对话流

摘要和压缩，thread 驱动的 harness 也有。差别在于 thread 迟早会结束，personal agent 的对话没有终点，用户消息、定时任务、交出去的工作跑完的通知，会一直接进来。

三个案例里能看到两种接法。Grok Bot 的重建代码里，每个 agent 只有一条对话流，用户消息、定时任务和工作完成的通知都进这一条。历史长了，就在原地压成摘要，记忆每轮放进系统提示〔20〕。Muse/Hatch 的主对话也是一条持续、会压缩的对话。定时任务和事件触发的检查，则交给脱离对话运行的 worker。按二进制里的提示词，worker 只拿到任务说明和记忆文件这类工作区文件，跑完把结果交回主 agent，由主 agent 决定怎么处理〔21〕。

Grok Bot〔3〕和 Muse/Hatch〔5〕的压缩是异步进行的，摘要在后台生成的同时，agent 还在接着处理新消息和通知。所以两家在换上摘要前，都会先补上摘要之后发生的事。压缩做得再及时，只要漏掉后来的变化，接下来的判断就可能建立在旧状态上。长期背景还是要靠记忆，任务做完没有，要看任务记录和工具结果。

摘要可以趁对话还在进行时提前准备，代价是多花一些模型调用。Codex 默认的上下文压缩〔7〕会让主线停下来，等压缩做完再继续。它最近加了后台压缩〔13〕，目前还在开发中，默认关闭。上下文快满之前，它先在后台生成摘要，turn 照常往下跑，主线只在把摘要换进来时停一下。要是摘要还没出来，上下文就先满了，主线还是得等。

Codex 还有一种由模型主动发起的方式〔14〕，也在开发中，默认关闭。开启后，Codex 会让模型知道上下文还剩多少，快用完时再提醒一次。模型可以自己决定换一个新的上下文窗口。这一步不生成摘要。工作过程中，模型会把之后还要用的信息记进自己的笔记，换了窗口，笔记还在。新窗口开头会带上一段笔记提示，模型可以接着读笔记，需要时也能查回旧历史。换窗口仍在主线上完成，但主线不用等模型写摘要。

背景留多少、摘要多早开始准备、什么时候必须停下来整理，要看这件任务能接受多少等待和成本。

新消息来了：先分清改的是哪件事

thread 里的新消息，基本都在说同一件事。personal agent 收到新消息时，手上可能同时挂着几件不相干的事，比如一条还在跑的长命令，或者一个正在处理子任务的 work agent session。它得先判断这条消息改的是哪一件。新消息可能让其中某件事变得多余，也可能改变它该做的内容。举个例子，用户让助手比较三家酒店，比到一半说只看第二家。还在查另外两家的 session 就该停掉。如果已经替用户给第一家发了询价邮件，邮件收不回，就补一封说明不用了。各个 session 的结果陆续回来，助手要分清哪个结果属于哪件事，再整理成一个回答告诉用户。

三个案例在这一步各有做法。Grok Bot 和 Codex 都能给还在跑的 work agent session 发新指令，必要时打断它这一轮，酒店例子里停掉多余的查询，靠的就是这个〔15〕〔16〕。Codex 的长命令有自己的进程 ID，新消息来了，对话可以照常往下走，但默认的压缩和普通工具调用进行时，主线还是得等。Muse/Hatch 会把新旧消息合成一个请求重新跑，能不能重跑，要看之前已经做到哪一步。

交出去以后：用户不在，也能做完

在 thread 里需要审批时，用户就在旁边。personal agent 交出去的事，往往在用户不在的时候跑，要能自己做完，做完先核对，再交回结果。碰到授权和需要用户拿主意的地方，请求得送到用户真能看到的地方，比如手机，可能要等上几个小时，这段时间别的事也不该跟着停。主线也得知道这件事卡在等用户。Codex 的审批是按 thread 设计的，子任务在等审批，主线 agent 看到的还是“在运行”，它跟用户说进度时，就可能说错。

中断以后，有了进度记录，恢复也更有依据。先要分清是哪种中断。主线不再等某条命令了，那条命令可能还在后台进程里跑，接着等它的结果就行。进程真正中断以后，则要先核实哪些步骤已经完成、有没有对外产生影响，再决定怎么继续。尤其是结果不确定的动作，直接重跑可能造成重复。记忆能帮它理解原来的目标，但实际做到哪一步，还得看任务记录和工具结果。

提醒和调度：thread 里没有的部分

thread 驱动的 harness 没有这一步，用户不开口，它就不动。personal agent 得自己决定什么时候开口。通知也要按最新情况来定。用户曾经收到过一条提醒，后面就不该因为重新发现同一件事再发一次。有新结果的时候，要结合最新情况判断现在值不值得说。需要用户拿主意的时候，带着已有进度回来问。助手越主动，这些判断就越影响用户愿不愿意继续把事情交给它。

最后还有调度。记住了要跟进，还得有东西到点把任务叫起来，再把结果送回负责处理的助手。记住背景、留住进度、按时推进、交回结果，少了哪一环，用户都可能重新变成那个追问和收尾的人。

从哪里开始

我自己搭 harness 时，会先挑几件真要交给它的工作，看哪些能拆出去自己跑，哪些阶段还得留在主线上等。也要看哪些信息得长期留着，哪些进度不能丢，哪些选择必须回来问我。再据此决定助手要多主动、工作拆到多细，以及愿意承担多少等待和运行成本。

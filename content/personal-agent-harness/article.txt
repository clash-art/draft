personal agent 的 harness 有什么不同

01 从对话窗口，到长期助手

Kevin Rose 在 Tim Ferriss 的播客〔1〕里讲过两件事，都是 Instinct 帮上了他的忙。第一次，Instinct 提醒他，几天前有一份 DocuSign 他还没签。第二次，Instinct 把取药通知、当天的航班状态和他的出发时间放在一起看，然后提醒他先去把药取了，再去机场。

这两次提醒，Kevin Rose 都没有先开口去问，提醒是自己来的。那份漏签的文件埋在他过去收到的信息里，取药的提醒又得结合他当天的安排才想得到。助手要给出这样的提醒，得先把这几条信息找出来，还得知道哪些事还没完成，哪些时间应该放在一起考虑。

也就是说，就算没人问，它也一直在跟着这些事。这正是我对 personal agent 最在意的一点。我把事情交给它以后，不用一直盯着它。它还在帮我查资料的时候，我可以接着跟它说新的安排。过几天我再回来找它，手里的项目也不用从头再讲一遍。

平时大家用得多的是 thread 驱动的 harness。开一个 thread，往往就是为了一件事，用户带着问题来，事情做完了，再开下一个 thread。如果我们一直找同一个助手，期待就会多一层。手头的事情可以换来换去，但之前交代过的背景和约定还在，没做完的事也有人接着跟进。这层期待能不能满足，要看背后的 harness 是怎么安排的。

举个例子，用户隔了几天回来，接着聊上周的项目。助手得记得之前聊到了哪里，哪些事已经定下来了。这几天项目要是有了新进展，它也得跟得上。用户的偏好可能几个月都适用，任务的状态却可能刚刚才变过。如果助手只会复述以前的聊天记录，就跟不上这些变化。

长期助手要满足的四个要求

持续在场：用户随时来找它，它都能马上回应。用户关掉窗口以后，交代给它的事也还在往下推进。要做到这一点，主要靠三件事。第一是抢占，用户发来的新消息，能先打断助手手上没那么急的工作。第二是把耗时的事交出去，长命令放进后台进程去跑，成块的工作交给专门的 work agent session 去做，这样主线就能腾出来，继续跟用户说话。第三是调度和交回，交出去的事要有人按时把它叫起来，做完以后要有人收下结果。比如记忆里写着“明天下午跟进”，到了时间却没有东西去触发它，这次跟进就落空了。又比如任务已经跑完了，结果却没有交回给用户，这件事也还不算办完。

快速响应：事情做到一半，用户提了新要求，助手得马上看到这条要求，还要让它影响接下来的动作。还没做的步骤，助手得重新看一遍要不要继续做。已经发出去的消息、已经提交的操作，不能当作没发生过，需要改的，就再补一条更正。助手还得弄清楚事情实际进行到了哪一步，跟用户说明哪些已经完成了，哪些还能停下来，哪些还要用户来决定。所以要看助手响应快不快，就看新要求进来以后，它要多久才能停下那些已经不需要再做的事。

少让用户操心（hands-off）：用户把事情交出去以后，不用盯着助手的每一轮推理和每一次工具调用。助手自己往下推进，做完以后先核对一遍结果，再交回给用户。该问用户的时候，助手仍然要问。比如超出了用户给的授权，或者发现目标对不上，又或者碰到需要用户拿主意的选择，助手就要带着当前的进度和几个选项回来，请用户决定。碰到权限边界的时候，助手不能自己就放行。如果事情中途被打断，或者暂时失败了，助手也要保留原来的目标和已经完成的进度，能接着做就接着做。某一步的结果不确定时，要先核对清楚，避免同一件事重复执行。交出去的事还得有个地方记着，哪些事还没办完、每件事各自在等什么，助手要随时都能说清楚。

主动发现下一步（proactive）：围绕用户已有的目标，从新进来的信息里找出值得接着做的事。助手发现一条线索以后，要先确认它仍然跟用户相关、还没有被处理过，再判断自己是不是已经得到许可去行动。就算可以去做，也还要判断值不值得现在就打扰用户。例行的进度可以先记下来，涉及用户要做决定的事，或者时间上拖不得的变化，再判断要不要立刻提醒用户。发现了、可以做、现在该说，是三个不同的判断。

这四个要求里，有一部分在 thread 驱动的 harness 里已经有现成的做法。Codex 和 Claude Code 都能把用户的新消息排到下一轮，或者插进当前这一轮，都能把长命令放进后台进程，也都能把子任务交给专门的 work agent session〔8〕〔9〕〔10〕〔13〕。对 personal agent 来说，在这些做法上需要做的优化有两类。

第一类，是改掉这些机制的默认做法。插进当前这一轮的新消息，在 Codex 里叫 steer。这种消息原本要等模型这一次输出完，或者等工具调用结束，才会交给模型，其他大多数 harness 现在也还是这样〔9〕。personal agent 需要的是新消息尽快影响助手正在做的事，效果接近抢占。Codex 最近的改动就接近这种做法。从 10 月发布的 0.163.0 正式版开始，Codex 默认打开了 instant_interrupt 这个开关，代码里管这种做法叫 preempt。开关打开以后，steer 消息一到，harness 就会取消正在进行的模型请求，把新消息并进上下文，再重新发一次请求。已经启动的工具照样会跑完，排到下一轮的消息也照旧等着〔11〕〔21〕。

第二类，是 thread 驱动的 harness 很少碰到的情况。要少让用户操心，就意味着用户多半不在场，助手得自己把事做完，该问用户的时候，再把请求送到用户面前。要主动发现下一步，该提醒用户什么、什么时候说，也都得助手自己判断。

02 三个案例怎么补上这四个要求

这三个案例的材料来源各不相同。Grok Bot 的材料来自非官方的重建代码，Muse/Hatch 的来自非官方的二进制归档，dots 的来自它底层的开源 Codex harness，以及泄露出来的 dots 提示词。

Grok Bot

Grok Bot 下功夫最多的是持续在场。用户发来新消息，别的 agent 交回结果，定时任务又到点了，这几件事可能同时到达。在群聊里还要再多一层。用户在群里说一句话，群里的几个 bot 会轮流发言，发言的轮数有上限，哪一轮没有 bot 说话，就停下来。每个 bot 在私聊和各个群里说过的话，都记在同一份记录里，群里的发言会标出来是哪个群〔2〕。这么多事情同时找上来，Grok Bot 该先处理哪一件？

根据 Grok Bot 的非官方重建代码〔2〕，用户、其他 agent、定时任务这三种来源的事，会进入三个不同的队列。Grok Bot 每次做完手上的事、要挑下一件事的时候，会先看用户队列里有没有消息。用户队列里没有，再看其他 agent 发来的消息。两边都空了，它才去处理定时任务，以及交出去的工作跑完后发回来的通知这类事。

一件事排在前面，也还要看它能不能抢占。其他 agent 发来的普通消息，要等 Grok Bot 当前这一轮工作结束才会处理。一对一发送时标成 priority 的消息，能打断对方手上那些不是用户交代的工作，马上把对方叫醒〔24〕。正在处理的用户任务是受保护的。所以，一条消息要多久才能生效，还得看它有没有抢占的权限，以及 Grok Bot 当前在忙什么。优先级消息能影响调度，但不能替用户批准对外的动作。

Grok Bot 也可以把工作交出去。Task 工具会把一块工作交给专门的 work agent session，可以让这个 session 在后台运行，跑完以后发一条通知回来〔12〕。这个 session 还在跑的时候，如果用户改了主意，主线可以打断它的这一轮，立刻给它换上新的指令。它跑完以后，主线还能接着用同一个 session，让它带着上一次的执行记录继续做。这几项能力都由开关控制，从重建代码里看不出线上默认打开了哪些。这个 session 不能直接跟用户说话，碰到需要授权的操作时，审批请求还是会送到用户面前〔14〕。

交出去的工作或者命令跑完以后，主线会被叫醒去看结果，但不会自动告诉用户。按照重建代码里叫醒主线时附带的指令，结果是新的、跟用户有关，或者用户说过要等这个结果，主线才会发一条消息告诉用户。结果如果已经过时、重复了，或者已经处理过了，这次叫醒就静默结束〔16〕。在这份重建代码里，把事做完和告诉用户，是两个分开的动作。

Grok Bot 用一份待办清单，记着用户交代下来的事。按照重建代码，主线只负责回话和派活，成块的工作交给 work agent session 去做，主线再用 TodoWrite 工具维护一份待办清单〔25〕。用户提了要求，主线先把它记成一条待办，再派出去。每条待办有四种状态：还没开始、进行中、已完成、已取消。如果有几个 session 同时在跑，就会有几条待办同时处在进行中。已完成指的是结果已经交到了用户手上，session 跑完了还不算。主线每次被叫醒，都要先对一遍清单，看看哪些在跑、哪些有了结果、下一步该派什么。这份清单存在对话状态里，压缩上下文的时候，最新的清单会原样带进摘要。如果服务中途断掉了，系统会核对还没跑完的工作和还没回复的消息，再叫醒主线把它们补上〔26〕〔27〕。

Muse/Hatch

Muse/Hatch 下功夫最多的是 proactive。Muse 的官方设计文章〔4〕里说，助手会按照时间和相关的事件持续做事，这些工作有了结果以后，再判断要不要提醒用户。下面讲的材料都出自那份归档。

Muse 主动找用户有三个入口。第一个是主动推送，每条推送只带一件值得打扰用户的事。这件事可能是记忆里值得一提的事、一个需要关注的目标、一封等着用户读的信，或者最近某次对话的后续，每条推送都会写明它来自哪里。第二个是 Feed，系统按自己定的时间表生成帖子，每一篇都是专门为这个用户写的。第三个是 Ideas，助手自己想出可以替用户做的事，用户点一下，它就去做〔32〕。

推送会自己控制节奏。普通的事，要等用户醒着、手头不忙的时候再送，一天最多送一次。时间要紧的事，限制会放宽一些，真正紧急的事就马上送。用户想多听到什么、不想听到什么、在什么时段听、用什么格式，都记在一个偏好文件里。Muse 每次写推送之前，都会把这个文件从头读一遍〔32〕。我认为这一层决定的是什么时候说，它跟说什么同样要紧。

每次挑选要推送的事，助手最多选一件，也可以一件都不选。候选的事要先和最近的对话、记忆、以往的送达记录对一遍，避免推送用户已经办完的事，或者用户已经收到过的同一条提醒〔5〕。

要持续发现新情况，也不必每次都启动一次完整的推理。定时任务负责到点触发。要看外面有没有变化，归档里还有一种事件 hook（event hook）。它用一个 Bash 轮询脚本去检查条件，条件成立的时候，才唤醒负责这件事的 agent〔5〕。Claude Code 的 Monitor 工具思路类似，也是让一个脚本一直盯着，脚本有输出了才通知模型。不过 Monitor 的每次监视都有期限，默认是 5 分钟，最长 30 分钟，到期就结束，会话结束了也会停〔31〕。Hatch 的事件 hook 跟定时任务一样，属于自动化的一种，按固定的间隔轮询，没有这个期限。我认为这让 Hatch 的 proactive 粒度更细。它可以盯住一个具体的条件，条件一变就叫醒负责的 agent，用不着等下一次定时任务，用户不在场的时候，它也能一直挂着。

Muse/Hatch 会把答应过用户的事建成跟踪项。拿机票举个例子，邮箱里来了一封航班确认邮件，助手不用去问用户，先查一下有没有同一趟行程的跟踪项。没有的话就建一个，再把比价和航班动态这两个定时任务挂到这个跟踪项上。跟踪项结束的时候，这两个任务也一起删掉〔28〕。预订、快递、提醒、出行这类超出当前对话范围的事，就算用户没说要跟，助手也要建一个跟踪项。东西订好了、款也付完了，只要后续还有事没完，这个跟踪项就一直开着。跟踪项和用户自己设的目标是分开存的。

每个跟踪项都有一行当前状态，写的是最新的结果、正在等什么，或者卡在了哪里。助手每记一条进展，系统都会看看这一行要不要跟着更新。如果用户说过某天之前还没回音就提醒我，这个条件就可以记成一条升级规则，到期的时候告诉用户，或者请用户来决定。每个跟踪项还配了一个笔记文件，用来记助手自己的工作笔记，助手接着做这件事之前，要先读一遍这个文件。跟踪项只分进行中和已完成两种状态。工具说明里要求，只要有证据表明事情已经结束，比如快递签收了、活动结束了、用户取消了，助手就要主动把跟踪项关掉。光是一直没有动静，或者只做完了其中一步，都不算结束。

对外发送、付款这类操作，每一次都要用户批准，审批请求会推送到用户的手机上〔15〕。归档里也有前后对不上的地方。文档里说，定时任务这类没人在旁边看着的任务，可以停在审批卡片上等用户。二进制里给脱离对话运行的 worker 的提示词却说，审批可能永远等不来，要把它当作失败，换别的办法。实际运行的时候按哪一种来，光看归档是判断不了的。

执行过程中来了新消息，只要模型还没有调用工具，也还没开始输出最终回复，Muse/Hatch 就会把旧的请求和新消息合成一个请求，重新跑一遍。如果工具已经发出去了，或者正在压缩上下文，又或者新消息的来源不同，新消息就要排到这一轮之后〔5〕。

dots/Codex

dots/Codex 这一节主要看两件事。第一件是 Codex 这一层怎么做快速响应。第二件是 dots 怎么做主动发现：Dreamer 负责去找新情况，要不要告诉用户，由主助手来决定。

OpenAI 的 Dominik Kundel 在一篇公开文章〔7〕里提到，dots 是基于开源的 Codex harness 做的。同一篇文章里还说，dots 会主动跟进工作，也能设置按时间或者按事件触发的自动化。主动跟进靠的是 dots 自己在上面加的一层。根据泄露的 dots 提示词〔22〕，主助手会派出一个叫 Dreamer 的调研 agent，按心跳定时运行。Dreamer 先读最近的对话、用户笔记和待办，再去用户已经连接的应用里找新情况。Dreamer 不能联系用户，也不能替用户做事。只有发现了有用的新东西，或者碰到需要主助手处理的阻碍时，它才会通知主助手一次，告不告诉用户，由主助手决定。每天凌晨还有一次复盘，回顾当天的对话，更新用户的偏好和优先级。Muse/Hatch 是让一个 agent 自己挑一件事去提醒用户，dots 则是让一个 agent 负责发现，另一个 agent 决定说不说。在开源的 Codex 里找不到 Dreamer，只能看到 Codex 把定时心跳触发的消息和用户亲自发的消息分开记录〔23〕。

Dreamer 读的那份待办，是共享记忆里的一个文件。根据泄露的 dots 技能说明，主助手会把用户重要的待办、承诺和截止日期都记在这里〔29〕。用户没提过、也还没开始做的事，只要对用户重要，也要记上。每条待办有四种状态：待办、进行中、已完成、已取消。卡点另外记三栏：这件事是不是卡住了，被清单里哪几条卡住了，现在在等谁。在等谁又分成几种，有等用户、等助手自己、等别人或者外部服务，以及什么都不等。只有确认结果已经达成，才能标成已完成。截止日期过了，也要先查清楚发生了什么。关掉的事会保留七天，然后挪进归档。这份文件由主助手或者负责记忆的 work agent session 来改。Dreamer 只读不改，调研完以后告诉主助手哪些该加、哪些该改、哪些该关〔22〕。

执行过程中来的新消息，和正在跑的工具，分别怎么处理，要看底层的 Codex。下面几段来自 Codex 的测试定义和源码，只能说明 Codex 这一层的情况，dots 线上的实现可能还有别的做法。

Codex 把模型推理、工具执行和整轮 turn 分开来管理。任务进行的过程中，用户的新指令有两种发法，steer 是插进当前这个 turn，queue 是排到下一轮〔8〕。插进当前 turn 的新指令，现在默认会直接中止当前的推理，但已经启动的工具还是会跑完〔6〕〔11〕〔21〕。推理停下来了，工具已经造成的外部影响不会自动撤销，得另外处理。工具如果还没做完，下一次推理也可能要等它。

遇到耗时长的命令，Codex 会先等一会儿。命令跑完了，就交回结果。没跑完的话，就交回一个进程 ID，之后接着查同一个进程，不用把命令重跑一遍。

打开还在开发中的 Code Mode 以后，模型写的代码片段也能这样转到后台继续跑。用户发 steer 时，这段代码会接着跑。用户直接打断这个 turn 的话，代码就会被终止，长命令的后台进程则会留下来〔11〕。

于是，助手得同时顾着两边。一边是用户已经聊到了新的事情，另一边是原来的命令或者代码可能还在跑。助手要用原来的标识继续去查，等结果回来以后，弄清楚这是哪件事的结果、现在还有没有用，以及它是不是已经对外部系统产生了影响。

03 自己搭 harness，哪些做法值得借鉴

三家各有所长。如果我们要自己实现一个 harness for personal agent，还得往下想五个技术问题。第一，几件事同时来了，谁先处理。第二，用户改主意的时候，正在做的事怎么停。第三，用户不在的时候，事情怎么记、怎么等。第四，助手什么时候该开口。第五，记住的东西怎么保持新鲜。下面一个一个来看，在每个问题上，各家有哪些做法值得借鉴。

几件事同时找上门，谁先说话

用户的消息排第一，这一点没什么争议。难的是别的事什么时候可以插队。在这个问题上，Grok Bot 的做法值得借鉴。用户、其他 agent、定时任务各排一个队，标成 priority 的消息能打断那些不是用户交代的工作，正在处理的用户任务则受保护〔24〕。主线只负责回话和派活，成块的工作都交给 work agent session，所以用户来找它的时候，主线总能回话〔12〕。我认为 Grok Bot 待办清单里对已完成的定义也值得借鉴，结果交到用户手上才算完成，session 跑完了还不算〔25〕。

用户改主意时，正在做的事怎么停

比如用户让助手比较三家酒店，比到一半，用户说只看第二家。这时候，还在查另外两家的 session 应该停掉。已经发出去的询价邮件收不回来，就再补发一封邮件说明情况。在这里，Codex 的 preempt 值得借鉴，新消息一到就中止推理，已经启动的工具照样跑完〔11〕〔21〕。如果工具还没发出去，Muse/Hatch 会把新旧消息合成一个请求重新跑〔5〕。对于已经派出去的 session，Grok Bot 和 Codex 都能给它发新指令，必要时还能打断它的这一轮〔12〕〔13〕。

压缩上下文的时候，也别让主线停下来等。常见的做法是等上下文快满了才压缩，主线一直等到摘要写完，这样最省 token。Codex 的提前压缩还在开发中，默认是关闭的。打开以后，它会在上下文用到 65% 时开始压缩，摘要一出来就换上，代价是压缩得更勤，作废的摘要也照样计费〔30〕。Grok Bot 和 Muse/Hatch 在压缩的时候还会接着处理新消息，换上摘要之前，先把压缩期间发生的事补进去〔3〕〔5〕。我认为 personal agent 值得多花这些 token，因为用户只想把事交出去，然后马上听到助手说一句记下了。

用户不在时，事情怎么记、怎么等

答应过用户的事，要有地方记下来。Muse/Hatch 的跟踪项值得借鉴。用户没说要跟，它也会建跟踪项，每个跟踪项有一行当前状态，拿到证据才关掉〔28〕。再加上 dots 待办文件里的那一栏，把每件事在等谁写清楚〔29〕。审批请求送到用户手机上〔15〕，在等用户审批的那几个小时里，别的事照常往下做。

至于等外部的变化，我认为 Muse/Hatch 的事件 hook 最值得借鉴。常见的做法是靠定时任务到点叫醒 agent 看一眼。这样就算没有变化，也要跑一次推理，可要是把间隔设长了，又会错过变化。Claude Code 的 Monitor 也是让脚本盯着，有输出才通知模型，可每次最长只能盯 30 分钟，会话结束也就停了〔31〕。Hatch 用一个轮询脚本检查条件，条件成立了才叫醒负责的 agent，没有期限，用户不在的时候也一直挂着〔5〕。盯票价、等快递、等对方回邮件，这些事都适合这样做。平时不用跑推理，条件一变，助手马上就能开口。

已经派出去的事，主线也要主动去查。Grok Bot 能看到还在跑的 session 最近调用了哪些工具，在告诉用户任务还在跑之前，它要先查一遍〔20〕。Codex 和 Claude Code 的主线默认只拿到最后的结果。

事情被中断以后，要先核实哪些步骤已经做完了、有没有对外部产生影响，再决定怎么继续。结果不确定的动作，如果直接重跑，可能会造成重复。

什么时候该开口

发现了、可以做、现在该说，是三个不同的判断。dots 把发现这一步交给 Dreamer，Dreamer 不能联系用户，说不说由主助手决定〔22〕。我认为 Muse 把现在该说这一步做得最细。每条推送只带一件事，普通的事等用户醒着、不忙的时候再送，一天最多一次。用户的偏好写进一个文件，写推送之前先读这个文件〔32〕。

记住的东西怎么保持新鲜

Grok Bot 每一轮对话结束，都会提取该记下来的事〔17〕。Muse/Hatch 每小时把新的对话合并进记忆一次，每晚再回看一遍〔18〕。这两家都比 Claude Code 记得更勤，Claude Code 是由模型自己判断要不要记〔19〕。记得多了，过时的东西也会多。两家都用新的说法覆盖旧的说法，Grok Bot 还会让旧的记忆慢慢淡出〔17〕〔18〕。压缩上下文的时候，再顺带换上最新的记忆，助手就不会照着上个月的偏好去办事。
